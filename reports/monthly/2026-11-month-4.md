## Community DevNet

### Chain halt and new genesis

On October 17 at 19:56 UTC the chain stopped at height 814730. Two governance proposals had changed `epoch_length` inside one epoch, and the chain then tried to create the same epoch a second time. The error is deterministic, so the old history was not recovered ([#267](https://github.com/paranjko/external-test-lab/issues/267), open).

DevNet restarted from a new genesis with the same chain ID. Genesis time is October 20, 12:06 UTC ([network history](../../devnet/NETWORK-HISTORY.md), [genesis record](../../devnet/genesis/7c76efc566f094fad5b221f331596673a206d79af79e5325cec6b40a9f78262e/README.md)). On October 29 all five P2P-active nodes held the full history of the new chain from block 1 ([#153](https://github.com/paranjko/external-test-lab/issues/153#issuecomment-6499725949)).

All results dated October 23 or later in this report are from the new chain.

## Testing and findings

### DevShard v6 on live DevNet

The tests below used the official builds on live DevNet with `Qwen/Qwen2.5-7B-Instruct`. Every v6 run used the `v6.0.0-rc1` gateway image. The figures are measured points for the executed windows, not guarantees.

- **Maximum throughput, October 23.** In a closed-loop run both versions passed up to 48 concurrent requests: v4.2 reached 5.61 requests/s and v6 reached 7.86 requests/s. The authors name the host GPUs as the limit in both cases ([results](https://github.com/paranjko/external-test-lab/issues/282#issuecomment-6414574471)).
- **One hour at 32 concurrent requests.** v4.2 completed 15,677 requests with no failures on October 25. v6 completed 20,795 requests with nine HTTP 502 responses on October 26. Both runs passed. They are not directly comparable: on October 25 two GPUs were throttling on heat. Gateway memory grew through the hour in every run ([results](https://github.com/paranjko/external-test-lab/issues/282#issuecomment-6414574471)).
- **Fixed rate, October 28.** v4.2 passed at 5 requests/s and v6 passed up to 10 requests/s. Above that the gateways returned HTTP 429. The authors note that the collapse starts before the hosts run out of capacity, so the measured maximum is lower than the stand can do ([results](https://github.com/paranjko/external-test-lab/issues/282#issuecomment-6498456720)).
- **Switch from v4.2 to v6, October 27.** The switch passed, with no failed requests within one minute of either switch point. With all traffic on v6 the stand served 5.86 requests/s, against 4.78 requests/s with all traffic on v4.2 ([results](https://github.com/paranjko/external-test-lab/issues/282#issuecomment-6489822044)).
- **Wrapper update under load.** On October 26–30 hosts moved to the `v6.0.0-rc1` wrappers with no failed user requests, but each updated host was quarantined for 60 minutes after a gap of 10–30 seconds ([results](https://github.com/paranjko/external-test-lab/issues/282#issuecomment-6442204411)). On November 3 five hosts moved to the `v6.0.0` wrappers in 1.5–2 minutes each, again with no failed client requests ([results](https://github.com/paranjko/external-test-lab/issues/298#issuecomment-6605385251)). The 4B hosts carried no client load during their updates.
- **Full stop of one host under load.** On November 1, with hosts on `v6.0.0-rc1`, the test failed: after the restart the host kept only one slot of each open escrow, clients saw 1.9% errors for about eight hours, and the validator was excluded for downtime ([results](https://github.com/paranjko/external-test-lab/issues/296#issuecomment-6570447897)). The defect is fixed upstream in `v6.0.0`. The rerun on November 3 passed with no errors in 46,800 requests, but the fix itself was not exercised: the open escrows were settled before the host returned to rotation ([results](https://github.com/paranjko/external-test-lab/issues/296#issuecomment-6609204828)). A regression test is in [PR #297](https://github.com/paranjko/external-test-lab/pull/297).
- **Three hours on `v6.0.0`, November 3.** At 6 requests/s the stand served 64,800 requests with no errors and a p95 latency of 7.36 seconds. The share of invalid validation votes varied between 13% and 45% by period, and its cause was not established ([results](https://github.com/paranjko/external-test-lab/issues/301#issuecomment-6620817437)).

### Local stand

Load and fault scenarios ran on a local network with real DevShard processes and mock chain, DAPI and ML nodes ([#254](https://github.com/paranjko/external-test-lab/issues/254)). These results do not establish behaviour on a live network.

- Normal load, a failing ML node, a slow ML node and a long escrow passed. Catch-up scenarios failed, with a ghost share of 13.2–14.5% against a 2% limit.
- A regression first attributed to [gonka#2003](https://github.com/gonka-ai/gonka/pull/2003) was withdrawn two days later: the cause was a 30-second execution timeout in the scenarios. Upstream raised it to 90 seconds ([correction](https://github.com/paranjko/external-test-lab/issues/254#issuecomment-6249799796)).
- In the rerun of seven upstream scenarios the findings per scenario fell from 4–11 to 1–2. Errors while an escrow is being replaced remain in every scenario ([results](https://github.com/paranjko/external-test-lab/issues/254#issuecomment-6262943183)).
- Combined faults and network, Postgres and full-disk faults were not pursued.

### Defects and upstream reports

Opened by the Lab in `gonka-ai/gonka` during the period:

- [gonka#2008](https://github.com/gonka-ai/gonka/pull/2008): the gateway ignores the configured first-token timeout floor once it has learned a p95 value.
- [gonka#2016](https://github.com/gonka-ai/gonka/issues/2016): the logprobs optimisation override is ignored after the gateway's first start.
- [gonka#2112](https://github.com/gonka-ai/gonka/pull/2112): draft tests showing that `tool_choice=required` becomes `auto` before token-budget enforcement.
- [gonka#2173](https://github.com/gonka-ai/gonka/issues/2173): the gateway admin API silently ignores updates of one throttle threshold.
- [gonka#2180](https://github.com/gonka-ai/gonka/issues/2180) with [gonka#2183](https://github.com/gonka-ai/gonka/pull/2183): `devshardd` releases the ML node slot before a streaming response is consumed, so the concurrency limit does not bound streaming work.
- [gonka#2194](https://github.com/gonka-ai/gonka/issues/2194): one model cannot start in MLNode `4.0.0-sigma2` on a Tesla T4.
- [gonka#2219](https://github.com/gonka-ai/gonka/issues/2219): the DAPI admin API cannot manage an ML node whose id contains a slash.
- [gonka#2249](https://github.com/gonka-ai/gonka/issues/2249): DevShard mempool limits, based on local regression evidence only.

The Lab also contributed load results to [gonka#2017](https://github.com/gonka-ai/gonka/pull/2017#issuecomment-6286981950) and reproduced [gonka#2104](https://github.com/gonka-ai/gonka/issues/2104#issuecomment-6442201941) on DevNet with the official `v6.0.0-rc1` gateway.

Open Lab defects without an upstream report yet: the chain halt on an `epoch_length` change ([#267](https://github.com/paranjko/external-test-lab/issues/267)), the gateway keeping sessions on a removed DevShard version ([#269](https://github.com/paranjko/external-test-lab/issues/269)) and a long prompt stalling the 4B queue ([#294](https://github.com/paranjko/external-test-lab/issues/294)).
