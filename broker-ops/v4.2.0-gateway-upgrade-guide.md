# Devshard gateway 4.2.0 — upgrade from 4.1.3

Official release: [Devshard Gateway v4.2.0](https://github.com/gonka-ai/gonka/releases/tag/release/gateway/v4.2.0)
(currently marked as a pre-release).

Run 4.2.0 with a new volume and new escrows. Keep 4.1.3 available for rollback
and settlement of its existing escrows.

Image:
```text
ghcr.io/gonka-ai/devshard-gateway:mainnet-v0.2.15-v4.2.0
```

Pinned digest:
```text
ghcr.io/gonka-ai/devshard-gateway@sha256:00b1870af42a4cd7e04f10c09ccb9d9bb26d87044ee813516c8b149813bc836c
```
Session protocol: `v4.2`. Route: `/devshard/v4.2`.

## 1. Prepare
- Save the current Compose configuration, image digest and full admin settings.
- Disable automatic settlement on the old gateway before starting the upgrade.
- Check free disk/RAM and choose an unused loopback API port.
- Check the chain registry for `v4.2`:
```bash
curl -fsS https://rpc.gonka.gg/chain-api/productscience/inference/inference/devshard_approved_versions
```
Keep the old volume separate. Do not import bound v4.1 escrows into v4.2 or
attach both gateways to the same storage.

## 2. Start the new gateway
Set `GATEWAY_V420_PORT` and the required keys in your deployment environment.
Add `docker-compose.v420.yml`:

```yaml
services:
  gateway-v420:
    image: ghcr.io/gonka-ai/devshard-gateway@sha256:00b1870af42a4cd7e04f10c09ccb9d9bb26d87044ee813516c8b149813bc836c
    restart: unless-stopped
    environment:
      DEVSHARD_PORT: "8080"
      DEVSHARD_API_KEYS: ${GATEWAY_API_KEY:?required}
      DEVSHARD_ADMIN_API_KEY: ${DEVSHARD_ADMIN_API_KEY:?required}
      DEVSHARD_PRIVATE_KEY: ${DEVSHARD_PRIVATE_KEY:?required}
      DEVSHARDS_JSON: "[]"
      DEVSHARD_CHAIN_ID: gonka-mainnet
      DEVSHARD_CHAIN_RPC: https://rpc.gonka.gg/chain-rpc/
      DEVSHARD_CHAIN_GRPC: none
      DEVSHARD_PUBLIC_API: https://node3.gonka.ai
      DEVSHARD_ROUTE_PREFIX: /devshard/v4.2
      DEVSHARD_STORAGE_DIR: /root/.devshardctl
      DEVSHARD_ESCROW_ROTATION_ENABLED: "false"
      DEVSHARD_ESCROW_ROTATION_SETTLEMENT_ENABLED: "false"
    volumes:
      - gateway_v420_data:/root/.devshardctl
    ports:
      - "127.0.0.1:${GATEWAY_V420_PORT:?required}:8080"

volumes:
  gateway_v420_data:
```

Include any additional overlays required by your deployment in every command.
Start only the new service; leave the front on 4.1.3.
```bash
docker compose -f docker-compose.yml -f docker-compose.v420.yml config --quiet
docker compose -f docker-compose.yml -f docker-compose.v420.yml pull gateway-v420
docker compose -f docker-compose.yml -f docker-compose.v420.yml \
  up -d --no-deps --no-build gateway-v420

A="http://127.0.0.1:${GATEWAY_V420_PORT:?required}"
H="Authorization: Bearer ${DEVSHARD_ADMIN_API_KEY:?required}"
curl -fsS "$A/v1/status" -H "$H"
```

## 3. Configure

### Required settings

**Automatic settlement must be disabled on both gateways before the upgrade
and remain disabled after switching traffic.** Check the live admin settings:

- `escrow_rotation.settlement_enabled: false`.
- Every `escrow_rotation.models[].settlement_enabled` override, if present, must be `false`.

Rotation and automatic settlement are separate settings. Enabling rotation
must not enable automatic settlement.

**Use the gateway defaults for concurrency per 10,000 weight. Do not raise them
or copy higher values from the old gateway:**

- Inference: `max_concurrent_requests_per_10000_weight: 5`.
- PoC: `poc_max_concurrent_requests_per_10000_weight: 10`.

```bash
umask 077
curl -fsS "$A/v1/admin/settings" -H "$H" > settings-v420.json
```
Edit the full returned document:
- Preserve new fields; transfer required model/token limits and redundancy settings.
- Keep both per-10,000 settings at the defaults specified above.
- Set the default model and offered models; use `access_mode: api_key` for client access.
- Keep `escrow_rotation.enabled` and `escrow_rotation.settlement_enabled` false.

```bash
curl -fsS -X POST "$A/v1/admin/settings" -H "$H" \
  -H 'Content-Type: application/json' --data-binary @settings-v420.json
curl -fsS "$A/v1/admin/settings" -H "$H" > settings-v420-confirmed.json
```
Bootstrap environment flags apply to a fresh database. Change live rotation
through the full admin settings document.

## 4. Create and check new escrows

If both gateways share a wallet, pause old rotation and wait for pending wallet
transactions to complete. Submit mint/settle transactions sequentially.

Set `MODEL` to the exact model ID and `AMOUNT_NGONKA` to the deposit in ngonka.
Create one new escrow per offered model:
```bash
curl -fsS -X POST "$A/v1/admin/escrows" -H "$H" \
  -H 'Content-Type: application/json' \
  -d "{\"amount\":${AMOUNT_NGONKA:?required},\"model_id\":\"${MODEL:?required}\",\"private_key_env\":\"DEVSHARD_PRIVATE_KEY\",\"route_prefix\":\"/devshard/v4.2\",\"register\":true}"
```
Save each ID and transaction hash. Confirm `code=0`, creator, epoch, model and
amount on chain before continuing. If mint succeeded but registration failed,
register that new ID through `/v1/admin/devshards` without `amount`.

Using the client gateway key, check each offered model:

- Non-stream response with valid content.
- SSE with content, finish reason and stream termination.
- Structured tool call.

Check `session_version: v4.2`, nonce advancement and model routability in status.
Resolve failures before moving traffic. Then provision enough escrows for the
current load; enabling rotation does not bootstrap an empty mid-epoch pool.

## 5. Switch traffic

Update inference and accounting together. For a front using these variables on
the same Docker network:
```text
GATEWAY_URL=http://gateway-v420:8080/v1
GONKA_ACCOUNTING_URL=http://gateway-v420:9091
```

Preserve the existing upstream mode and required overlays. Recreate only the
front service. A restart may interrupt open SSE connections.

Verify client requests and accounting through the front. Update monitoring
URLs, targets, epoch-exporter volume mounts and operator tools to the new slot.
Keep the old gateway running while its requests and cleanup finish.

Enable rotation only on the new gateway after checks pass. Automatic settlement
must remain disabled, including per-model overrides. Keep the per-10,000 defaults. Observe availability, errors, latency, cleanup, resources
and escrow creation under normal traffic.

## Rollback

1. Check that the old pool can serve traffic.
2. Pause new rotation and wait for pending wallet transactions.
3. Restore old inference and accounting upstreams; recreate only the front.
4. Restore old rotation, monitoring and operator targets; keep automatic settlement disabled.
5. Keep the new gateway and volume until its requests drain and escrows settle.

Do not run the old binary on new-version storage or remove either volume.
